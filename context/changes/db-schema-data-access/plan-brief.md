# DB Schema & Data-Access Layer — Plan Brief

> Full plan: `context/changes/db-schema-data-access/plan.md`

## What & Why

Set up Drizzle ORM + postgres.js, define the three PostgreSQL tables (`lessons`, `sessions`, `transcripts`), generate the initial SQL migration, write a typed data-access layer (DAL), and wire automated migration into the GitHub Actions deploy pipeline. This is Foundation F-01 — every downstream slice (S-01 lesson CRUD, S-02 voice session, S-03 session library) imports from `@/db` and cannot be built without it.

## Starting Point

The project is a bare Next.js App Router scaffold with zero database tooling. No ORM, no migration files, no `src/app/api/` routes exist. The only signal is a `DATABASE_URL` placeholder in `.env.production.example` and an existing VPS PostgreSQL instance. The `@/*` path alias is wired in `tsconfig.json`, so `@/db` imports will resolve once the folder exists.

## Desired End State

All three tables are live in the VPS PostgreSQL database. Any file under `src/` can import typed functions — `createLesson`, `getAllSessions`, `saveTranscript`, etc. — from `@/db` with no `any` types. Pushing to `main` automatically migrates the database before restarting PM2, so schema and code are always in sync.

## Key Decisions Made

| Decision | Choice | Why (1 sentence) | Source |
|---|---|---|---|
| ORM / driver | Drizzle ORM + postgres.js | TypeScript-first, lightest footprint, no binary engine | Plan |
| Transcripts design | One row per session, JSONB `messages` array | Single JOIN loads full conversation for LLM context; satisfies FR-010 resume at zero extra complexity | Plan |
| Migration workflow | drizzle-kit generate → SQL files checked in → migrate on deploy | Full audit trail, idempotent, zero manual intervention on deploy | Plan |
| Vocabulary field | Plain `TEXT` column | Passed verbatim to AI system prompt; no downstream query on individual terms in v1 | Plan |
| Session label | Derived at query time via JOIN to lessons | Free conversations get a fixed "Free conversation" label; avoids a title snapshot column | Plan |
| DAL layout | `src/db/schema.ts` + `src/db/client.ts` + `src/db/queries/*.ts` | DB concerns grouped together, queries colocated with the table they touch | Plan |
| Migration in CI | SCP `db/migrations/`; SSH `drizzle-kit migrate` before PM2 restart | Requires no new secrets; `node_modules/` copy already ships `drizzle-kit` to the VPS | Plan |

## Scope

**In scope:**
- Drizzle ORM + postgres.js installation
- `src/db/schema.ts` — three table definitions + `Message` type
- `src/db/client.ts` — singleton postgres.js pool + Drizzle instance
- `drizzle.config.ts` — drizzle-kit configuration
- `db/migrations/0000_*.sql` — initial migration (generated, not hand-written)
- `src/db/queries/lessons.ts` — 5 CRUD functions
- `src/db/queries/sessions.ts` — 7 session/transcript functions
- `src/db/index.ts` — barrel export
- `.github/workflows/deploy.yml` — SCP + SSH migrate step

**Out of scope:**
- API routes (S-01, S-02)
- Voice pipeline, shadcn/ui, Vercel AI SDK (F-02)
- Seed data
- Migration rollback strategy
- `drizzle-kit push` (never used)

## Architecture / Approach

```
src/db/
  schema.ts       ← table definitions + Message type (source of truth for types)
  client.ts       ← postgres.js singleton + drizzle(client, { schema })
  queries/
    lessons.ts    ← getAllLessons, getLessonById, createLesson, updateLesson, deleteLesson
    sessions.ts   ← getAllSessions, getSessionById, createSession, endSession,
                     deleteSession, saveTranscript, getTranscriptMessages
  index.ts        ← re-exports everything above

db/migrations/    ← SQL files generated by drizzle-kit (committed)
drizzle.config.ts ← points drizzle-kit at schema + migrations folder
```

All imports use `@/db` (resolves to `src/db/index.ts`).

## Phases at a Glance

| Phase | What it delivers | Key risk |
|---|---|---|
| 1. Install, schema, initial migration | Packages installed; schema.ts + client.ts + drizzle.config.ts created; `db/migrations/0000_*.sql` generated and applied to VPS | Migration SQL differs from schema intent — caught by manual SQL inspection |
| 2. Typed data-access layer | All 12 DAL functions typed and verified against live DB | Type errors or missing query patterns discovered during round-trip test |
| 3. CI/CD wiring | deploy.yml migrates DB automatically on every push to main | `source .env.production` in SSH step fails to expose DATABASE_URL — fixable by switching to explicit env var passing |

**Prerequisites:** VPS PostgreSQL is running and `DATABASE_URL` is set in `.env.production` on the VPS.  
**Estimated effort:** ~1 session across 3 phases.

## Open Risks & Assumptions

- `DATABASE_URL` in `.env.production` on the VPS is assumed to be correctly configured before running migrations. No validation is added at app startup.
- `drizzle-kit` is a devDependency but is shipped to the VPS via the `node_modules/` SCP copy. If the deploy strategy changes to a production-only `npm ci --omit=dev`, this breaks — move `drizzle-kit` to regular dependencies at that point.
- The `source .env.production` approach in the SSH migrate step assumes the file uses simple `KEY=VALUE` lines (no complex shell quoting). The current `.env.production.example` confirms this format.

## Success Criteria (Summary)

- `psql $DATABASE_URL -c "\dt"` on the VPS shows `lessons`, `sessions`, `transcripts`
- `import { createLesson } from '@/db'` compiles with full TypeScript types, no `any`
- Pushing to `main` triggers automatic migration; a subsequent `npx drizzle-kit migrate` on the VPS reports "No migrations to run"
